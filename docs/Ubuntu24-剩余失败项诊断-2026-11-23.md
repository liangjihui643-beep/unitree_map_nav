## 3. 水洼项：测试夹具缺前提，且能力含义混淆

### 复现与证据

```text
tests/test_competition.py::test_rendered_puddle_is_confirmed_by_lidar_and_blocks_planning
tests/test_competition.py:109: assert polygons
E   assert []
```

诊断：

```text
image (240, 320, 3), points 72
support_plane = None
navigation_support = False (simulation_config 默认)
water_detection = False (simulation_config 默认)
hsv_nonzero = 3535, regions = 1, area = 3535
polygons = 0, last_sources = []
```

### 原因

- 测试直接构造裸 `GridMap`，灌一帧点云后调用 `WaterDetector.detect()`。
- `simulation_config()` 默认 `water_detection=False`，检测器会在入口直接返回空；测试没有先开启。
- 颜色辅助分支还要求 `navigation_support=True` 且 `support_plane` 有效；测试两者都没有。
- 即使补上这两个前提，`colour_support_candidate()` 输出的来源是 **`rgb_stance_keepout_candidate`**，含义是“RGB + 支撑面的避让候选”，不是“激光确认水洼”。当前测试名和断言把两种能力混在一起。

### 修改方案

**A. 改这条测试为 RGB+支撑面避让测试**

- 显式设置 `water_detection=True`、`navigation_support=True`；
- 用与测试姿态一致的支撑面（不要给 `GridMap` 默认塞一个平面）；
- 断言来源为 `rgb_stance_keepout_candidate`；
- 断言该候选加入 hazard 后，规划/`traversable()` 确实避让。

**B. 保留独立的激光确认测试**

- 用有足够近地回波、能形成局部平面的拟合夹具；
- 断言来源为 `lidar_ground_colour`，并保留面积/位置检查；
- 不要再要求同一条 RGB 分支同时承担“激光确认”。

不建议给 `GridMap` 默认添加 `support_plane`，也不建议放宽检测器。

## 4. 稀疏角落项：单帧用于“安全拒绝”，逃逸用例要补观测

### 复现与证据

```text
tests/test_competition.py::test_sparse_observed_corner_has_collision_checked_se2_escape
tests/test_competition.py:160: assert len(route) > 2 ...
E   assert (0 > 2)
```

诊断：

```text
points 72
floor_finite 21, seen 85, traversable 21
start cell (200,200): seen=True, floor=0.0, logodds=-0.45, traversable=True
start footprint safe=False
route shape (0,3)
```

### 原因

- 只有一帧 72 点激光，地图只形成 21 个可信地面格。
- 起点中心格可通行，不代表带安全边距的整块足迹可通行。
- `Explorer.maneuver()` 检查每段动作的中间姿态和完整足迹；起始足迹未确认安全时返回空路径，符合现有安全设计。
- 该测试不应把“单帧未知”与“已观测后的逃逸”混为一个用例。

### 修改方案

**A. 保留单帧负向用例**

断言起始足迹无法确认安全时，`maneuver()` 返回空路径；这是安全拒绝，不是缺陷。

**B. 新增/改写正向逃逸用例**

- 补有明确地面支撑的地图夹具；
- 补观测时要换视点，重复灌入同一帧不会增加可见范围；
- 保持原足迹尺寸、安全边距和逐段碰撞检查；
- 断言逃逸距离、转角、完整足迹安全。

不建议为让空路径变成非空而放宽足迹/安全边距。

## 5. 坡道项：先对齐正式坡道运行配置

### 复现与证据

```text
tests/test_mujoco.py::test_lidar_adapted_mpc_advances_up_official_ramp
tests/test_mujoco.py:290: assert data.qpos[1] > 4.88
E   assert 4.5878... > 4.88
```

### 已发现的配置差异

- 测试直接创建 `ConvexMPC`，其 `terrain_slope_limit_deg` 默认是 **15°**（`mpc_locomotion.py:203`）。
- 正式仿真每步设置：

```python
controller.terrain_slope_limit_deg = max(15., float(config.slope_limit(last_step.pose.xy())))
```

（`mujoco_sim.py:627`）

- MPC 在 `terrain_slope_limit_deg > 15.` 时才切换到坡道步态/坡面处理（`mpc_locomotion.py:426` 附近）。测试与正式仿真可能走了不同的控制路径。
- 当前 `Config` 的 `lidar_elevation_center_deg` 仍是 `-22.5`；文档 `SENSOR_ASSUMPTIONS.md:39` 记录过对称 FOV 会导致 y=4.62。当前失败不能只用 FOV 中心解释，但也不能排除高度带/地形估计的差异。

### 修改顺序

1. 让测试复用正式坡道工况的区域配置和坐标换算；
2. 记录实际 `terrain_slope_limit_deg`、当前步态、`terrain_plane` 坡度、`terrain_updates`、近地支持点数；
3. 跑一次定向对照；
4. 若对齐后通过，只修测试入口；
5. 若仍停在 y≈4.59，交给运控同学检查地形估计和触地跟踪；保留原 `y>4.88` 验收线。

不建议先改 MPC 参数；先排除测试入口和运行配置差异。
